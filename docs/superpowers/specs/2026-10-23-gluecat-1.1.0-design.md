# gluecat 1.1.0: per-catalog Hadoop options, inherited S3 role, HTTP client settings, IAM-enforced tests

Date: 2026-10-23. Extends the 1.0.0 design (`2026-10-22-gluecat-design.md`); its binding sections stay binding.
This document adds three features and one testing change. Its own "Decided" section is binding in the same way.

## Why

Deployments configure one gluecat catalog per Glue account and give each catalog its own IAM role for Glue. The data
behind those tables sits in S3 buckets that the same role can read, but gluecat 1.0.0 leaves S3 access to the
session-wide Hadoop S3A configuration: the only per-catalog lever is Hadoop's per-bucket configuration
(`fs.s3a.bucket.<name>.*`), which means listing every bucket of every catalog in the Spark configuration. Iceberg's
Glue catalog does not have this problem: with `AssumeRoleAwsClientFactory` the catalog role is used for Glue, STS and
S3 alike, and `spark.sql.catalog.<name>.hadoop.<key>` overrides the Hadoop configuration per catalog.

Second, Iceberg catalogs accept `http-client.*` settings (client type, timeouts, pool size, proxy). Deployments already
set them in shared catalog configuration; gluecat ignores them and uses the SDK's default HTTP client.

Third, the 1.0.0 test suite runs against MiniStack with IAM off, so nothing proves which Glue actions gluecat needs
or how it behaves when a call is denied. MiniStack 1.5.31 enforces IAM with `AUTH=true` (verified 2026-10-23: user
and role policies, trust policies, cross-account AssumeRole, web identity, and the reset endpoint all work; root
account keys bypass policies).

## Goals

1. **Per-catalog Hadoop options.** `spark.sql.catalog.<name>.hadoop.<key> = <value>` is applied to every table the
   catalog loads, creates or replaces, through the mechanism Spark and Delta already honour for table options. Same
   key shape as Iceberg.
2. **Inherited S3 role, on by default.** A catalog with `client.assume-role.arn` makes S3A assume that role for the
   files of its tables, with no further configuration. Same behaviour as Iceberg's `AssumeRoleAwsClientFactory`.
3. **HTTP client settings** for the Glue and STS clients, with Iceberg's `http-client.*` names.
4. **IAM-enforced integration tests.** CI runs MiniStack with `AUTH=true`; the suite runs under a role whose policy
   lists exactly the Glue actions gluecat uses, and that policy becomes the documented IAM policy.
5. **A guide to multiple catalogs in multiple AWS accounts** (owner request, 2026-10-23): one documentation page
   that explains the assume-role model end to end, so a reader can set up N catalogs over N accounts and regions
   without reading the code.
6. Release as 1.1.0 (new options and a new default behaviour, no breaking API change).

## Non-goals

- `glue.skip-name-validation`, `glue.lakeformation-enabled`, Iceberg's `s3.*` FileIO properties, DynamoDB catalog or
  lock manager. gluecat does no data IO of its own; the Hadoop equivalents are reachable through `hadoop.*`.
- Managing Hadoop's `FileSystem` cache. The cache key is scheme, bucket and user, not the configuration, so the
  first access to a bucket in a JVM (driver or executor) fixes that bucket's credentials and endpoint for every later
  access; two catalogs with different roles on the same bucket share the first `FileSystem`, and a direct path read
  with the session configuration poisons the bucket for the catalog. gluecat does not disable the cache (a new,
  never-closed `S3AFileSystem` per configuration on every executor task is a leak), it documents the rule that
  follows: one bucket is reached one way only, through one catalog's role or through the session configuration.
- Per-catalog options for direct path access (`delta.\`s3://...\``, `spark.read.parquet(...)`). Those never reach a
  catalog.
- IAM enforcement in the compatibility suites (Trino, legacy Hive client). Their MiniStack stays with IAM off.

## Anti-goals

- Writing any derived or user-supplied `hadoop.*` value into Glue. The Glue entry format is unchanged.
- Changing any 1.0.0 option name, default, or the Glue entry format. The only behaviour change is goal 2, and it is
  the behaviour the option name already promises in Iceberg.
- Logging credentials or session tokens. Derived keys are logged by name at `initialize`, never with secret values
  (role ARNs and regions are fine).
- A second configuration surface for S3. There is `hadoop.*` and the derived defaults; no `s3.*` group.

## Decided

- **Option group `hadoop.`**: every option whose key starts with `hadoop.` is a Hadoop configuration override for this
  catalog; the key after the prefix is used as is. Unknown keys are not warned about (they are Hadoop's to validate).
- **Where overrides go** (amended 2026-10-23 after Task 3 showed Delta ignores `option.*` keys on creates and copies them
  into the Delta log's `metaData.configuration`, which would expose the role ARN in `SHOW TBLPROPERTIES`):
  1. *Loads*: into the storage properties of the `CatalogTable` the catalog hands out (Delta tables through
     `DeltaFormatSupport`, other tables through the core). Delta copies `fs.*` and `dfs.*` keys from
     `catalogTable.storage.properties` into the `DeltaLog` Hadoop configuration (verified in Delta 4.3.0,
     `DeltaTableV2.deltaLog`); Spark applies every storage property of a V1 table to its data source's Hadoop
     configuration. Reads, inserts, time travel, `REFRESH` and parquet tables are covered this way.
  2. *Staged writes* (CTAS, `REPLACE ... AS SELECT`, `CREATE OR REPLACE ... AS SELECT`, `writeTo`): as write options on
     the `WriteBuilder` of `StagedGlueTable` (`LogicalWriteInfo.options` plus the catalog's keys); Delta's write path
     builds its Hadoop configuration from them and writes nothing of them into the log.
  3. *Everything else that opens the table's location* (plain `CREATE`, `REPLACE` without `AS SELECT`, the by-path
     `loadTable` after a create or staged commit, `SET LOCATION`'s existence check): gluecat first opens the
     location's `FileSystem` with the catalog's Hadoop configuration (`Path.getFileSystem(hadoopConf)`), so that
     Hadoop's cache holds an instance built with the catalog's options before Delta or Spark ask for one with the
     session configuration. This is the one-bucket-one-way rule applied by gluecat itself; it relies on the cache
     being enabled (Hadoop's default), which the documentation states.
  Never as `option.<key>` table properties: Delta persists those in the table's metadata.
- **Injected values never reach Glue**: injection happens on the objects handed to Spark and Delta, never on the
  table specification gluecat persists. Create, replace and alter write the Glue entry from the user's properties
  alone. A unit test asserts that a catalog with `hadoop.*` options writes the same Glue entry as one without.
- **Derived S3 defaults** (goal 2), when `client.assume-role.arn` is set and `client.credentials-provider` is not:

  | Hadoop key | Value |
  |---|---|
  | `fs.s3a.aws.credentials.provider` | `org.apache.hadoop.fs.s3a.auth.AssumedRoleCredentialProvider` |
  | `fs.s3a.assumed.role.arn` | `client.assume-role.arn` |
  | `fs.s3a.assumed.role.session.name` | `client.assume-role.session-name` (default `gluecat`) |
  | `fs.s3a.assumed.role.session.duration` | `client.assume-role.timeout-sec` as `<n>s` |
  | `fs.s3a.assumed.role.external.id` | `client.assume-role.external-id` when set (Hadoop 3.4+ reads it; 3.3 ignores it, documented for Spark 3.5) |
  | `fs.s3a.endpoint.region` | `client.region` when set |
  | `fs.s3a.assumed.role.credentials.provider` | the session's `fs.s3a.aws.credentials.provider`, only when the session leaves the base key unset and its provider is not `AssumedRoleCredentialProvider` itself (builder check, 2026-10-23: Hadoop's default base is static plus environment credentials, which cannot do web identity, so IRSA deployments would fail on the first S3 call without this row) |

  Not derived: `fs.s3a.assumed.role.sts.endpoint` and `.sts.endpoint.region`. Hadoop refuses a signing region
  without an endpoint, and the right endpoint depends on the partition and on VPC or FIPS use; S3A's default (the
  global STS endpoint) is what per-bucket deployments use today. Catalogs that need a regional or private STS
  endpoint set both keys under `hadoop.`. Key names verified against `hadoop-aws` 3.3.4 and 3.4.2 class constants
  on 2026-10-23.

  Reading the session's S3A settings for the base-provider row happens once at `initialize`, from the active
  session's Hadoop configuration (`spark.hadoop.*`); the derived map is then fixed for the catalog's lifetime.
- **Precedence**: explicit `hadoop.<key>` beats a derived value for the same key; derived beats the session's base
  `fs.s3a.*` keys; the session configuration is the fallback. Session per-bucket keys (`fs.s3a.bucket.<name>.*`)
  beat both, because `S3AFileSystem` copies them over the base keys at initialisation; the design keeps that (an
  upgrading deployment's per-bucket roles keep working unchanged) and documents it. Setting
  `hadoop.fs.s3a.aws.credentials.provider` yourself is the opt-out from the derived role; there is no separate switch.
- **No derivation** for catalogs without a role, or with a custom `client.credentials-provider` (S3A cannot reuse an
  arbitrary SDK provider class). Such catalogs still honour explicit `hadoop.*` keys.
- **`http-client.*`** with Iceberg's names and semantics, applied to the Glue client and the STS client of the
  catalog:
  `http-client.type` (`apache` | `urlconnection`; unset and no other `http-client.*` key means the SDK's own default
  resolution, which keeps 1.0.0 behaviour; unset with `http-client.apache.*` or proxy keys present implies `apache`,
  Iceberg's default, so shared Iceberg settings take effect; unset with only `http-client.urlconnection.*` keys
  implies `urlconnection`; keys for both types without a type is a configuration error at `initialize`), `http-client.proxy-endpoint`,
  `http-client.proxy-use-system-property-values`, `http-client.proxy-use-environment-variable-values`,
  `http-client.urlconnection.socket-timeout-ms`, `http-client.urlconnection.connection-timeout-ms`,
  `http-client.apache.socket-timeout-ms`, `.connection-timeout-ms`, `.connection-acquisition-timeout-ms`,
  `.connection-max-idle-time-ms`, `.connection-time-to-live-ms`, `.expect-continue-enabled`, `.max-connections`,
  `.tcp-keep-alive-enabled`, `.use-idle-connection-reaper-enabled`. A setting for the other client type than the one
  selected is ignored with a warning. `software.amazon.awssdk:apache-client` and `url-connection-client` 2.24.6 are
  `provided` and `optional` dependencies; selecting a type whose client is not on the classpath fails at
  `initialize` with a message naming the artifact. Unknown `http-client.*` keys warn and are ignored, like `glue.`
  and `client.`.
- **IAM-enforced tests**: the CI MiniStack service and `make ministack-up` run with `AUTH=true`. `SparkFixture`
  bootstraps, in every account a suite uses, a role `gluecat-test` whose trust policy allows the account root and
  whose inline policy allows exactly `glue:CreateDatabase`, `glue:GetDatabase`, `glue:GetDatabases`,
  `glue:UpdateDatabase`, `glue:DeleteDatabase`, `glue:CreateTable`, `glue:GetTable`, `glue:GetTables`,
  `glue:UpdateTable`, `glue:DeleteTable` on `Resource: "*"`; the main catalog of every suite uses
  `client.assume-role.arn` to that role. A Glue action outside that list fails the suite. The same policy is
  published in the documentation as the IAM policy gluecat needs (MiniStack's Glue resource ARNs are coarser than
  AWS's, so the published policy keeps `Resource: "*"` and tells readers how to scope it). `CredentialsIT` keeps a
  default-chain (root key) test and gains: a read-only role (`glue:Get*`) that lists databases and gets
  the access-denied error on `CREATE DATABASE` (the 1.0.0 error translation, asserted on the message and cause,
  no new exception class); a role whose trust policy excludes the caller, which fails on the first
  statement (not at `initialize`, which stays free of AWS calls as decided for 1.0.0) with an error naming the
  catalog and the role ARN. The compatibility compose file is unchanged.
- **Documentation page `multi-account.md`** as specified under Documentation; generic account IDs, bucket and role
  names only.
- **Compatibility suite covers the Spark 4.1 Glue Hive client too** (owner request, 2026-10-23): a second legacy
  container, `ghcr.io/sdaberdaku/spark-with-glue:4.1.3-scala2.13-java21-python3-ubuntu` with Delta 4.4.1 added at start,
  runs the same three interoperability tests as the Spark 3.5.1 one; the 3.5.1 container stays for the older entry format.
- **Version 1.1.0**, CHANGELOG entry listing the new options, the new default S3 behaviour and the test change.

## Constraints

- The 1.0.0 constraints hold: no `private[sql]` Spark objects, Scala 2.12 and 2.13, Java 8 bytecode for Spark 3.5,
  SDK 2.24.6 `provided`, MiniStack 1.5.31.
- Hadoop S3A assumed-role support exists in both Hadoop lines gluecat meets (3.3.4 with Spark 3.5, 3.4.x with
  Spark 4); `fs.s3a.assumed.role.external.id` only in 3.4.
- Delta forwards only `fs.*` and `dfs.*` storage properties; other Hadoop keys reach V1 data sources but not Delta.

## Design

### Option parsing

`GlueCatalogOptions` gains `hadoop: Map[String, String]` (explicit, prefix stripped) and `httpClient` settings. A
pure function `S3RoleDefaults.derive(options): Map[String, String]` produces the table above or an empty map; the
effective per-table Hadoop options are `derive(options) ++ hadoop` (explicit wins). Computed once at `initialize`,
logged once at info level by key, without values for keys whose name contains `secret`, `token` or `key` (none of
the derived ones do).

### Injection points

- `GlueCoreCatalog` wraps every `CatalogTable` it returns from `loadTable` with
  `storage.properties ++ effectiveHadoopOptions` (the table's own options win) before handing it to `V1TableBridge`.
- `DeltaFormatSupport`: the `CatalogTable` it builds for `DeltaCatalog` (including the schemaless view) gets the same
  storage properties; `StagedGlueTable.newWriteBuilder` merges the catalog's options into the write options; before
  every by-path `createTable`, `stageCreate`, `stageReplace`, `stageCreateOrReplace`, by-path `loadTable` and the
  `_delta_log` check in `alterTable`, `TableHadoopOptions.prime(location)` opens the location's `FileSystem` with
  `hadoopConf(session conf)`.
- `REFRESH TABLE` and `ALTER` re-sync read the Delta log through the table Delta loaded, so they inherit the options.
- `grep -rn newHadoopConf src/main` shows only calls that go through `TableHadoopOptions` and the one in
  `GlueCatalog.initialize` that reads the session configuration for `S3RoleDefaults.userSet`.
- No injected key is ever written to Glue or to the Delta log: the Glue entry comes from the user's properties
  alone, and a test asserts both the Glue entry and `SHOW TBLPROPERTIES` are identical with and without `hadoop.*`.

### HTTP client

`GlueClients` builds an `SdkHttpClient` from `http-client.*` when `http-client.type` is set, and passes it to both
client builders; otherwise the builders are left to the SDK (unchanged from 1.0.0). Proxy settings apply to both
client types through their `ProxyConfiguration` builders.

### Testing

- Unit: option parsing for `hadoop.` and `http-client.`; `derive` for the four cases (role, role plus explicit
  override, custom provider, no role); Glue entry equality with and without `hadoop.*`.
- Integration (MiniStack, `AUTH=true`): a catalog whose `hadoop.fs.s3a.endpoint` and credentials point at MiniStack
  S3 while the session's S3A configuration points at an unreachable endpoint; Delta CTAS, insert, read, time travel,
  `REFRESH`, and a parquet table create and read must all succeed through the catalog, and `spark.read.parquet` on
  a path in a *different* bucket (never touched through the catalog) must fail, which proves the override is per
  catalog and respects the one-bucket-one-way rule. Hadoop's `FileSystem` cache stays enabled, as in production: each
  catalog and each assertion uses its own bucket, so the first touch of every bucket is the one under test. A second catalog with the
  derived role defaults against a MiniStack role proves `derive` end to end: S3A assumes the role (MiniStack logs
  the `AssumeRole` with the session name). `http-client.type=urlconnection` and `apache` each run one Glue call;
  the full suite runs under the `gluecat-test` role; the negative credential tests above.
- The CI matrix is unchanged.

### Documentation

- `configuration.md`: `hadoop.*` and `http-client.*` tables, the derived S3 defaults table, precedence and opt-out.
- New section in `how-it-works.md`: why the options travel as table storage properties, what Delta and Spark do
  with them, the `FileSystem` cache caveat, and the direct-path limitation.
- `operations.md`: "IAM permissions" with the policy JSON and the note on scoping resources.
- README: three lines in the configuration example (`hadoop.` example, `http-client.type`), one sentence on the
  inherited role.
- `quickstart.md`: the two-account example no longer needs per-bucket S3A settings and links to the new page.
- New page `multi-account.md`, "Catalogs across AWS accounts", in the navigation after the configuration page.
  Contents, in this order:
  1. The identity model: one base identity per Spark application (the SDK default chain: IRSA on EKS, a profile on
     a laptop), one role per catalog assumed from it, and what each client uses (STS with the base identity; Glue
     with the role; S3A with the role through the derived defaults; Iceberg catalogs do the same with their own
     client factory). A diagram of one application, two catalogs, two accounts, two regions.
  2. The IAM pieces and who owns each: the base identity's `sts:AssumeRole` grant naming each role; each role's trust
     policy naming the base identity (with the external ID when used); the role's Glue policy (the published minimal
     policy); the role's S3 policy; bucket policies when the bucket's account differs from the role's account; the
     Glue resource policy alternative for `glue.id` without a role, and why a role is the recommended route.
  3. Regions: `client.region` (Glue and S3 endpoint region), `client.assume-role.region` (STS), what happens when
     the catalog's region differs from the application's default region, and reading a catalog in another region.
  4. Sessions: duration, refresh on the calling thread, what an expired or revoked role looks like in an error
     message, and that every error names the catalog and the role ARN.
  5. S3 in detail: the derived defaults table, the opt-out, when to add explicit `hadoop.*` keys (custom endpoint,
     requester pays), the `FileSystem` cache caveat and the one-role-per-bucket rule it implies, and direct path
     access staying with the session configuration. A dedicated example of one role for Glue and another for S3
     (`client.assume-role.arn` plus `hadoop.fs.s3a.assumed.role.arn`, the split Trino offers with
     `hive.metastore.glue.iam-role` and `s3.iam-role`), and a small table mapping gluecat's keys to Trino's and
     Iceberg's equivalents (`glue.id`, catalog role, data role, region, external ID).
  6. A worked example: the full Spark configuration for two catalogs in two accounts plus the three IAM documents
     (identity policy, trust policy, Glue policy), with generic names (`111111111111`, `acct_a`, `s3://bucket-a`).
  7. Troubleshooting: the common `AccessDenied` messages from STS, Glue and S3 and what each one means.
